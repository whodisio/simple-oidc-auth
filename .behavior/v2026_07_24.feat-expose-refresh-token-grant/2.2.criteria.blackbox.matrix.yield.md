# 2.2.criteria.blackbox.matrix — getTokensFromOidcRefreshClaims

coverage matrices distilled from `2.1.criteria.blackbox.yield.md`. the contract has three
largely-orthogonal concern groups, so it splits into three matrices rather than one
combinatorial explosion (see decomposition note at the end).

---

## matrix A — provider response → result vs typed error (the discrimination core)

the primary behavior: one independent variable (what the provider answers) maps to exactly
one observable outcome (a result, or one of three typed errors). this is the pit-of-success
guarantee from usecases 1, 3, 4, 5, 6.

| ind: provider response | dep: outcome | dep: thrown type | dep: `instanceof` base | dep: caller recovery |
|------------------------|--------------|------------------|------------------------|----------------------|
| 200, valid token body | resolves | — | — | use the access token |
| 400 `invalid_grant` | throws | `OidcTokenRefreshExpiredError` | `ConstraintError` (✋) | re-auth |
| 400 `invalid_scope` | throws | `OidcTokenRequestRejectedError` | `ConstraintError` (✋) | reduce scope claim |
| 400 `invalid_request` | throws | `OidcTokenRequestRejectedError` | `ConstraintError` (✋) | fix the request |
| 401 `invalid_client` | throws | `OidcTokenRequestRejectedError` | `ConstraintError` (✋) | fix operator creds |
| 429 `Too Many Requests` (rate limit) | throws | `OidcTokenEndpointMalfunctionError` | `MalfunctionError` (💥) | back off + retry (honor `Retry-After` → `retryAfterMs` metadata) |
| 5xx (e.g. 503) | throws | `OidcTokenEndpointMalfunctionError` | `MalfunctionError` (💥) | back off + retry |
| transport error (socket drop / refused / timeout) | throws | `OidcTokenEndpointMalfunctionError` | `MalfunctionError` (💥) | back off + retry |
| 200, body without `access_token` (malformed success) | throws | `OidcTokenEndpointMalfunctionError` | `MalfunctionError` (💥) | back off + retry (provider fault) |
| non-JSON / malformed error body (4xx/5xx) | throws | classifies by status band (4xx→Rejected, 5xx→Malfunction) via defensive read | per band | no raw `TypeError` — the body is read defensively |

covers usecases: 1, 3, 4, 5, 6 (incl. the 429 rate-limit sub-case), + boundary "success without access_token".

**coverage note (not a gap):** `invalid_request` has no dedicated usecase in 2.1 — it is
covered by usecase.4/5's class (`OidcTokenRequestRejectedError`) as a peer `invalid_*`
request fault. added here for symmetry so the row is not silently absent.

## matrix B — success-response shape → output fields

on a 200, two independent success-body variables (did it rotate? was `expires_in` present?)
map to the two variable output fields. `access` is always present, so it is not a dimension.

| ind: refresh_token in body | ind: expires_in in body | dep: `result.refresh` | dep: `result.expiresAt` |
|----------------------------|-------------------------|-----------------------|-------------------------|
| absent | present | `null` | `IsoTimeStamp` (≈ now + expires_in) |
| present, != input | present | the new token (non-null) | `IsoTimeStamp` (≈ now + expires_in) |
| present, == input | present | reflects it (non-null) | `IsoTimeStamp` (≈ now + expires_in) |
| absent | absent | `null` | `null` |
| present, != input | absent | the new token (non-null) | `null` |

covers usecases: 1 (row 1), 2 (row 2), 7 (rows 1 & 4), + boundary "refresh_token == input".

**symmetry read:** `result.refresh` is a pure function of the `refresh_token` dimension;
`result.expiresAt` is a pure function of the `expires_in` dimension. the two output fields
are independent — no cross-term — which is why the 2×2(+1) grid has no unexpected cells.

---

## matrix C — input claims → wire request + provider-honored outcome

two independent input-claim variables (`scope`, `resource`) map to what is sent on the wire
and the honored outcome. (the rejection cases when a claim is refused live in matrix A.)

| ind: `claims.scope` | ind: `claims.resource` | dep: scope param sent | dep: resource param sent | dep: honored outcome |
|---------------------|------------------------|-----------------------|--------------------------|----------------------|
| `null` | `null` | none | none | full grant, no audience restriction (common case) |
| `[]` (empty) | `null` | none | none | treated as null — no scope reduction |
| subset of grant | `null` | space-delimited scope | none | fresh token, reduced scope |
| `null` | absolute uri | none | the uri | fresh token, audience-restricted |
| subset of grant | absolute uri | space-delimited scope | the uri | fresh token, reduced scope + audience-restricted |

covers usecases: 1 (row 1), 8 (rows 3 & 4), + boundaries "scope null / resource null / scope
empty".

**note:** the "scope exceeds grant" input is deliberately NOT in matrix C — it does not
produce an honored outcome; it produces `invalid_scope`, which lives in matrix A. a split of
honored-vs-rejected across two matrices avoids a conflation of "what we send" with "how the
provider judges it."

## gap analysis

| candidate combination | covered? | note |
|-----------------------|----------|------|
| every provider-response class → a typed outcome | ✅ matrix A | all `invalid_*`, 5xx, transport, malformed |
| rotation present / absent | ✅ matrix B | usecases 1, 2 |
| expires_in present / absent | ✅ matrix B | usecase 7 |
| scope null / empty / subset | ✅ matrix C | usecase 8 + boundaries |
| resource null / set | ✅ matrix C | usecase 8 |
| scope > grant | ✅ matrix A (`invalid_scope`) | rejection, not honored — correctly in A |
| rotation × expires_in cross-terms | ✅ matrix B | all 5 meaningful rows enumerated |
| the three failure families are mutually distinguishable | ✅ matrix A | the discrimination guarantee |

no unspecified combination remains. every row in every matrix traces to a 2.1 usecase or a
boundary condition.

---

## decomposition signal

the full contract has ~4 independent variables (provider-response, rotation, expires_in,
scope/resource). a single flat matrix would be ~8 × 5 × 2 = large and mostly meaningless
cross-terms. the split into **three concern-scoped matrices** is the decomposition:

- **A (provider response → outcome)** — the failure-discrimination concern
- **B (success body → output)** — the success-shape concern
- **C (input claims → request)** — the input-claim concern

these are orthogonal: a matrix-A error path never reaches matrix-B output logic, and
matrix-C inputs are what *provoke* some matrix-A rows but are judged by the provider, not
by us. the three-matrix split keeps each grid small, symmetric, and independently
verifiable — a signal the behavioral boundaries are well-drawn, not that the usecase is too
broad.
