# 1.vision — getTokensFromOidcRefreshClaims (refresh_token grant)

vision for the wish at `0.wish.md` (source of truth: `whodisio/simple-oidc-auth#13`).

---

## the outcome world

### day-in-the-life

today, `simple-oidc-auth` owns exactly one leg of the oauth-2.0 dance: **code -> tokens**
(`getTokensFromOidcResponseClaims`). a user finishes the browser login, hands over their
`code`, and gets back tokens. that access token lives for ~1 hour, then dies.

when it dies, the only tool the library offers is "send the human back through the whole
browser login again." there is no quiet re-mint. the refresh token the provider issued at
login sits unused, because the library has no verb that spends it.

the consumer feeling this pain is **rhachet keyrack's `EPHEMERAL_VIA_OAUTH`** feature: it
wants to silently re-mint an access token every day from the stored refresh token, with
zero human involvement. it cannot, because the leg does not exist here — so keyrack would
have to hand-roll its own token-endpoint http call, re-deriving provider knowledge that
`simple-oidc-auth` already owns.

### before / after

| | before | after |
|---|--------|-------|
| code -> tokens | `getTokensFromOidcResponseClaims` ✅ | unchanged ✅ |
| refresh -> tokens | absent — consumers hand-roll axios | `getTokensFromOidcRefreshClaims` ✅ |
| access token expired | force full browser re-login | silent re-mint from refresh |
| refresh rotated by provider | invisible — lost | surfaced on `result.refresh` |
| refresh dead vs bad request vs server hiccup | one opaque throw for all | three typed classes: re-auth vs fix-request vs retry |

### the "aha" moment

the value clicks when keyrack's daily cron wakes, calls `getTokensFromOidcRefreshClaims`, and:

- **happy path** — gets a fresh access token, no human, no browser.
- **rotation** — the provider handed back a *new* refresh token; keyrack sees it on
  `result.refresh` and writes it back atomically. the old one is now dead, and keyrack
  knew in time to swap it.
- **dead refresh** — the provider says `invalid_grant`; keyrack catches a *typed,
  distinguishable* error that says "re-auth required" and routes the human back to login —
  instead of blindly retrying a token that will never work again.
- **server hiccup** — a `503` or a dropped socket throws a *different*, retryable error;
  keyrack backs off and tries again, instead of nuking a perfectly good refresh token.

the whole point: **the caller can tell these four outcomes apart from the return + throw
shape alone.** that discrimination is the feature, not the http call.

## user experience

### who the users are

- **primary user**: rhachet keyrack `EPHEMERAL_VIA_OAUTH` (machine caller, daily cron).
- **general user**: any backend holding a stored refresh token that wants a fresh access
  token without a browser round-trip.

### usecases / goals

1. **silent refresh** — spend a stored refresh token for a fresh access token.
2. **rotation capture** — detect + persist a newly-issued refresh token (single-use
   rotation, e.g. google/okta style).
3. **dead-refresh detection** — know, unambiguously, when the refresh token is spent so
   the human is routed back to full login.
4. **transient-failure survival** — distinguish a retryable server/network blip from a
   permanent grant failure, so a good refresh token is never discarded over a hiccup.

### contract inputs & outputs (testdrive)

symmetric with `getTokensFromOidcResponseClaims`: same `{ claims, provider, operator }` shape.
the `claims` are a named `OidcRefreshClaims` bundle — a set of **unverified assertions** we
present to the provider, which adjudicates them. (differs from `OidcResponseClaims` only in
*where* verification happens: response-claims are verified locally via hash + pkce; refresh-
claims are verified remotely by the provider. both are "claims" = asserted, not yet proven.)

```ts
import type { IsoTimeStamp } from 'iso-time';
import {
  getTokensFromOidcRefreshClaims,
  getTokenEndpointByOidcIdentityProvider,
  OidcIdentityProvider,
} from 'simple-oidc-auth';

const tokens = await getTokensFromOidcRefreshClaims({
  claims: {
    token: { refresh },        // the credential claim — "this token is valid & ours"
    scope: null,               // null = inherit the full originally-granted scope
    resource: null,            // null = no audience restriction on the issued token
  },
  provider: {
    tokenEndpoint: getTokenEndpointByOidcIdentityProvider(OidcIdentityProvider.GOOGLE),
  },
  operator: { oidcClientId, oidcClientSecret },
});

// tokens.access    -> string                (fresh access token, always)
// tokens.refresh   -> string | null         (the NEW refresh token if rotated, else null)
// tokens.expiresAt -> IsoTimeStamp | null    (absolute instant the access token dies, else null)
```

**the `OidcRefreshClaims` bundle** (why a named object, not a bare `refreshToken`): the
refresh request carries **three unverified assertions**, and none is trusted until the
provider rules. we cannot trust the token is valid, that it is ours, that we are entitled to
the grains we ask for, or that the target is right — the provider adjudicates every one.

```ts
interface OidcRefreshClaims {
  /**
   * the token claim — "this refresh token is valid and belongs to this operator"
   * - rejected by the provider as `invalid_grant` (rfc-6749 §5.2/§6)
   *   ("invalid, expired, revoked, or was issued to another client")
   */
  token: { refresh: string };

  /**
   * the scope claim — WHICH grains of access to mint into the new token
   * - MUST be a subset of the originally-granted scope (rfc-6749 §6)
   * - null = inherit the full original grant (the common case)
   * - rejected by the provider as `invalid_scope` when it exceeds the grant
   */
  scope: string[] | null;

  /**
   * the resource claim — WHICH target service/audience the token is for (rfc-8707)
   * - an absolute uri; audience-restricts the issued access token
   * - null = no audience restriction (the common case)
   */
  resource: string | null;
}
```

all three are nullable, not optional (`rule.forbid.undefined-attributes`): the key is always
present, so a caller consciously states each claim — `null` is the explicit "no assertion"
value, never a silently-absent key. the wire mapping joins `scope` space-delimited (rfc-6749
§3.3) and sends `resource` verbatim, only when non-null.

**why `expiresAt` (absolute), not `expiresIn` (a bare-number duration):**
- the wish sketched `expiresIn: number`, but a bare-number time is an `any-time` shape the
  house forbids (`rule.forbid.any-time` — hidden unit, no compiler guard).
- the caller's real need is "when do i refresh next" = an absolute instant = `IsoTimeStamp`
  (iso-time's stamp-vs-duration split: "when it happens" = stamp).
- we convert once at the boundary — `expiresAt = addDuration(now(), { seconds: expires_in })`
  — with the freshest clock read, so the caller does no `now() + x` math (and cannot get the
  latency-drift bug from doing that math later).
- cost: adds an `iso-time` dependency (not yet installed). worth it — this is exactly the
  case the adopted glossary exists for.
- `| null` when the provider omits `expires_in` (defensive; google always returns it).

**why not let the caller decode the access token's `exp`?** a jwt access token embeds an
`exp` claim — but oauth-2.0 access tokens are *opaque by spec* (rfc-6749 §1.4: "usually
opaque to the client"). google's access tokens are opaque strings with no decodable `exp`;
the id_token (the guaranteed jwt) is not returned on the refresh path. so the response's
`expires_in` is the one provider-uniform, spec-guaranteed source of the lifetime. we convert
from it once at the boundary, so the caller never introspects a token whose format it must
not assume.

### timelines (given / when / then)

**happy refresh, no rotation**
- given: a live refresh token, valid operator creds
- when: `getTokensFromOidcRefreshClaims(...)`
- then: resolves `{ access: <fresh>, refresh: null, expiresAt: '2026-07-24T15:30:00Z' }`

**happy refresh, with rotation**
- given: a live refresh token from a provider that rotates
- when: `getTokensFromOidcRefreshClaims(...)`
- then: resolves `{ access: <fresh>, refresh: <new>, expiresAt: '2026-07-24T15:30:00Z' }`
- and: the old refresh token is now spent (caller must persist `result.refresh`)

**expired refresh (re-auth path)**
- given: a revoked/expired refresh token
- when: `getTokensFromOidcRefreshClaims(...)`
- then: **throws `OidcTokenRefreshExpiredError`** (`extends ConstraintError`, ✋,
  non-retryable), the `invalid_grant` provider signal in metadata → caller re-auths

**rejected request (fix-request path)**
- given: a live refresh token, but a `scope` claim that exceeds the original grant
- when: `getTokensFromOidcRefreshClaims(...)`
- then: **throws `OidcTokenRequestRejectedError`** (`extends ConstraintError`, ✋), the
  `invalid_scope` signal in metadata → caller narrows the claim; a retry as-is never works

**endpoint malfunction (retry path)**
- given: the token endpoint returns `503` (or the socket drops / times out)
- when: `getTokensFromOidcRefreshClaims(...)`
- then: **throws `OidcTokenEndpointMalfunctionError`** (`extends MalfunctionError`, 💥) → the
  caller backs off and retries rather than discarding a good refresh token

## mental model

### how a user describes it to a friend

> "it's the other half of the login handshake. one function turns the login `code` into
> tokens; this new one spends the leftover `refresh` token to get a fresh access token —
> so you don't have to make the user log in again every hour. and it tells you *why* it
> failed: 'your refresh is dead, log back in' versus 'server hiccuped, try again.'"

### analogies / metaphors

- **the code grant is check-in; the refresh grant is the room key re-swipe.** check-in
  (code -> tokens) happens once at the desk. after that, you re-swipe the key card
  (refresh -> access) at your door each time it de-magnetizes — no trip back to the desk.
  when the card is truly dead (`invalid_grant`), *then* you go back to the desk (re-auth).
- **rotation = the door hands you a new card on each swipe.** you must pocket the new one
  (`result.refresh`) or your next swipe fails.

### terms — theirs vs ours

| the domain / rfc word | our word |
|-----------------------|----------|
| refresh_token grant (rfc-6749 §6) | `getTokensFromOidcRefreshClaims` |
| refresh_token (input credential) | `claims.token.refresh` |
| scope (rfc-6749 §6) | `claims.scope` |
| resource / audience (rfc-8707) | `claims.resource` |
| access_token | `access` |
| refresh_token (rotated, returned) | `refresh` |
| expires_in | `expiresAt` (absolute `IsoTimeStamp`) |
| token endpoint | `provider.tokenEndpoint` |
| client_id / client_secret | `operator.oidcClientId` / `operator.oidcClientSecret` |
| error=invalid_grant (rfc-6749 §5.2) | `OidcTokenRefreshExpiredError` (re-auth) |
| error=invalid_scope / invalid_request / invalid_client | `OidcTokenRequestRejectedError` (fix request) |
| 5xx / network error | `OidcTokenEndpointMalfunctionError` (retry) |

we keep the caller in *domain* words (`access`, `refresh`, `operator`, `provider`) and
hide the wire words (`grant_type`, `client_secret`, form-urlencoded) exactly as the code
grant already does.

## evaluation

### how well it solves the goals

- **silent refresh** — directly delivered by the happy path.
- **rotation capture** — delivered by surfacing `refresh` on the result (the wish's #1
  required behavior).
- **expired vs rejected vs malfunction** — delivered by the three-way error classification
  (the wish's #2 required behavior, widened by the scope/resource claims). this is the
  load-bearing design decision.

### pros

- reuses the token-endpoint + provider registry `simple-oidc-auth` already owns — keyrack
  duplicates nothing.
- the refresh grant is genuinely simpler than the code grant (no pkce, no hash, no
  csrf/pinj checks, no redirect_uri), so the surface is small and safe.
- sits beside `getTokensFromOidcResponseClaims` as a sibling first-class primitive — the
  library becomes a complete oauth-2.0-base pair.

### cons / tradeoffs

- **asymmetric output shape.** the code grant returns `{ identity, access }`; this returns
  `{ access, refresh: string | null, expiresAt: IsoTimeStamp | null }`. no `identity` (the
  refresh grant does not reliably re-issue an id_token). the *call* is symmetric; the *return*
  is not. this is honest to the rfc but breaks the "perfectly symmetric" story in the wish
  title.
- **new error-classification surface.** today the codebase throws a single
  `UnexpectedCodePathError` for every `status >= 300` (see groundwork). the wish demands we
  *split* that three ways (expired / rejected / malfunction). this is net-new typed-error
  infrastructure over the `helpful-errors` bases — the biggest design fulcrum (see open
  questions).
- **new test harness.** the wish's acceptance wants "a local rfc-6749 token endpoint."
  none exists today (unit mocks axios; the one integration test is `.skip`-ped, real, and
  manual). we must stand up a local fake token server.

### edgecases & pit-of-success

| edgecase | how the contract keeps the caller safe |
|----------|----------------------------------------|
| provider rotates refresh token | `result.refresh` is non-null → caller is *forced* to see it (not buried) |
| provider does NOT rotate | `result.refresh` is `null` (explicit), never `undefined` — caller must handle both |
| refresh revoked/expired (`invalid_grant`) | `OidcTokenRefreshExpiredError` (✋) → caller re-auths, never loops |
| token endpoint 503 / socket drop | `OidcTokenEndpointMalfunctionError` (💥) → caller backs off, never discards a good token |
| bad client creds (`invalid_client`, 401) | `OidcTokenRequestRejectedError` (✋) → fix-creds, distinct from a dead refresh |
| scope claim exceeds original grant (`invalid_scope`) | `OidcTokenRequestRejectedError` (✋) → caller narrows the `scope` claim, does not retry as-is |
| `scope: null` / `resource: null` | the common case — sent as absent wire params → inherit full grant, no audience restriction |
| access token present but no `expires_in` | `expiresAt: null` (explicit) — caller decides, never a silent guess |

the pit of success is the **discrimination**: a caller that does the obvious thing (catch
the error, read `result.refresh`) cannot accidentally discard a live token on a hiccup, and
cannot loop forever on a dead one.

## open questions & assumptions

### assumptions made

1. **the same token endpoint serves both grants.** confirmed — `grant_type` selects the
   grant; the endpoint per provider is identical (rfc-6749 §3.2, and the extant registry).
2. **client auth is via `client_id` + `client_secret` in the body**, to match the extant
   code-grant exchange. (rfc-6749 §2.3.1 names http-basic as the preferred method and body
   fields as merely "MAY"; the current code uses body fields, so we mirror it. note: apple's
   `client_secret` is itself a signed jwt via the extant `computeOidcClientSecretForApple` —
   the caller supplies the already-computed secret, so this leg stays provider-agnostic.)
3. **the refresh grant is provider-uniform enough to reuse one function.** true for google
   and generic rfc-6749 providers (keyrack's target). NOT universally true: facebook uses a
   non-standard long-lived-token exchange rather than the rfc-6749 `refresh_token` grant, so
   the registry's facebook endpoint is not a drop-in here. the wish's example targets google;
   we scope the guarantee to standards-compliant providers and flag facebook as out-of-scope.
4. **`identity` is not part of the refresh result.** the refresh grant returns an
   access_token + optional refresh_token + expires_in; an id_token is not guaranteed. keyrack
   only needs `access`, so we omit `identity`.
5. **network errors (no http response) are retryable.** with `validateStatus: () => true`,
   axios still throws on ECONNREFUSED / timeout — we treat those as transient/retryable.

### open questions (triaged)

each tagged `[answered]` (resolved now), `[research]` (defer to research phase), or
`[wisher]` (only the wisher can decide). no `[research]` items — every question resolves by
logic/house-style now, save the one design preference that is the wisher's to make.

- **Q1 (error taxonomy — the big fulcrum) — `[resolved by wisher, one part reopened]`.** how
  should the failure classes surface?
  - **(a) — CHOSEN:** typed error classes, caller does `instanceof`.
  - (b) one error class with a `.retryable: boolean` (or `.reason` enum) field.
  - (c) a `.classification` discriminant on a single error type.
  **decision (wisher, 2026-07-24): option (a) — typed error classes.** matches the repo's
  per-concern error-class pattern (`PotentialOidcAttackError`,
  `OidcAuthenticationResponseMalformedError`) and gives the cleanest `instanceof` at the
  keyrack call site.
- **Q1b (how many classes + names) — `[resolved by wisher]` — reopened by the scope/resource
  decision, then settled.** the `scope`/`resource` claims add a **third** failure family: a
  rejected request (`invalid_scope`/`invalid_request`) is a **caller-config** error — the
  refresh token is alive, but the request asked wrong. it is neither "re-auth" (token is fine)
  nor "retry" (a retry of the same bad request never works). so the two-way split becomes a
  **three-noun triad** — one noun per failed subject (Refresh · Request · Endpoint):
  - **`OidcTokenRefreshExpiredError`** `extends ConstraintError` (✋) — `invalid_grant` → the
    **refresh** credential is dead → **re-auth**
  - **`OidcTokenRequestRejectedError`** `extends ConstraintError` (✋) — `invalid_scope` /
    `invalid_request` / `invalid_client` → the **request** params/creds are bad → **fix the
    request** (non-retryable, non-re-auth)
  - **`OidcTokenEndpointMalfunctionError`** `extends MalfunctionError` (💥) — 5xx / socket /
    timeout → the **endpoint** broke → **retry**

  **decision (wisher, 2026-07-24): the three-noun triad above.** rationale:
  - **noun-first symmetry** — Refresh · Request · Endpoint, each with its state (Expired ·
    Rejected · Malfunction). names *what* failed, not a grab-bag (`rule.require.order.noun_adj`,
    ubiqlang). all group under `OidcToken*` for autocomplete.
  - **fault-axis reuse** — each extends the right `helpful-errors` base for its fault axis
    (caller ✋ `ConstraintError` vs server 💥 `MalfunctionError`); reuse the extant http/exit/
    emoji semantics rather than reinvent. (note: the two **extant domain errors** —
    `PotentialOidcAttackError`, `OidcAuthenticationResponseMalformedError` — cover neither
    transience nor rejection; both are code-grant browser-response concerns. so all three are
    genuinely new domain errors. they will also be the first repo domain errors to extend the
    `helpful-errors` bases — the two old ones are bare `extends Error`; we do NOT retrofit them,
    out of scope.)
  - **`Expired` caveat** — `invalid_grant` also covers revoked / wrong-client (rfc-6749 §5.2),
    so `Expired` is the dominant-but-not-sole cause; the exact provider reason rides in the
    error metadata. kept as the intuitive caller-facing name; recovery is identical (re-auth)
    for every `invalid_grant` cause.
  - keyrack sends `scope: null` / `resource: null`, so it never trips the Rejected class — but
    the class must exist because the claims now can be set. the blueprint hardens all three +
    their index exports.
- **Q2 (output on non-rotation) — `[resolved by wisher]`.** `refresh: null` vs omit the key.
  **decision (wisher, 2026-07-24): `refresh: string | null` (nullable, not optional).** the
  repo forbids `undefined` attributes on internal contracts; nullable keeps the key always
  present so the caller is forced to handle both branches (the rotation signal is never
  silently absent). the wish's `refresh?` sketch is reconciled to `| null`.
- **Q3 (expiry representation) — `[resolved by wisher]`.** the wish sketched `expiresIn:
  number` (seconds). **decision (wisher, 2026-07-24): return `expiresAt: IsoTimeStamp | null`
  instead** — an absolute instant, not a bare-number duration. rationale: (1) `expiresIn:
  number` is an `any-time` shape the house forbids (`rule.forbid.any-time`); (2) the caller
  needs an absolute instant to schedule the next refresh, so the contract computes
  `addDuration(now(), { seconds: expires_in })` once at the boundary rather than push `now() +
  x` math (and its latency-drift bug) onto every caller; (3) `| null` when the provider omits
  `expires_in`. cost: adds the `iso-time` dependency (not yet installed) — flagged for the
  blueprint/install stone.
- **Q4 (implementation shape) — `[answered]`.** a twin `exchangeRefreshTokenForTokens` in
  `domain.operations/exchange/` (mirrors `exchangeOidcResponseCodeForTokens`) under a thin
  `getTokensFromOidcRefreshClaims` wrapper, vs one flat function. resolved as a blueprint-stage
  detail; best-guess **twin exchange + wrapper** for symmetry, decided at the architect stone.

### must validate first

- **Q1/Q1b** (error-taxonomy shape + count) — **resolved by wisher 2026-07-24: option (a),
  three typed error classes** (`OidcTokenRefreshExpiredError` / `OidcTokenRequestRejectedError`
  / `OidcTokenEndpointMalfunctionError`, over the `helpful-errors` bases). no open items

## groundwork

### external research

verified against **rfc-6749** (https://datatracker.ietf.org/doc/html/rfc6749):

- **§6 refreshing an access token** — request is `grant_type=refresh_token` +
  `refresh_token` (required) + `scope` (optional); success response follows §5.1 and *may*
  include a new `refresh_token` (rotation) and includes `expires_in`. ✅ matches the wish's
  `{ access, refresh?, expiresIn }`.
- **§5.2 error response** — `invalid_grant` = "provided authorization grant is invalid,
  expired, revoked, ..." → the **refresh-expired / re-auth** signal. `invalid_scope` /
  `invalid_request` / `invalid_client` (typically `400`/`401`) → the **request-rejected**
  signal. errors are "typically 400 bad request." ✅ grounds the three-way classification.
- **rfc-8707 resource indicators** (https://www.rfc-editor.org/rfc/rfc8707) — the `resource`
  request param names the target service/audience for the issued token, valid on a refresh
  token request, distinct from `scope`. ✅ grounds the `claims.resource` claim.
- **network-layer failures** are outside the http error body — no `error` field, they throw
  at the transport layer → grounds the "transient/retryable" bucket.

### internal research

extant behavior this extends (verified, with paths):

- **sibling function** — `src/domain.operations/response/getTokensFromOidcResponseClaims.ts`:
  input `{ claims, provider: { tokenEndpoint }, operator: { oidcClientId, oidcClientSecret } }`,

- **provider registry (reuse as-is)** —
  `src/domain.operations/wellknown/provider/getTokenEndpointByOidcIdentityProvider.ts` +
  `src/domain.objects/OidcIdentityProvider.ts` (`GOOGLE` / `APPLE` / `FACEBOOK`). the wish's
  example call uses exactly this.
- **export surface** — `src/index.ts` (line 10 exports `getTokensFromOidcResponseClaims`); we
  add a sibling export line, plus any new error classes (lines 7-8 show the extant error

- **test conventions** — `*.test.ts` = unit (mocks `axios`, snapshot of call args, see

  `.skip`-ped real-provider manual test. **no local token-endpoint harness exists yet** — the

### repo naming / structure to conform to

- functions live in `src/domain.operations/<verb-group>/`, one export per file, filename ===
  function name.
- nested `provider` / `operator` input shape; domain words out (`access`, `refresh`,
  `expiresIn`).
- lowercase comments, `.what` / `.why` headers, no shouts.

## what is awkward

1. **the symmetry is partial.** the wish sells this as "symmetric with
   `getTokensFromOidcResponseClaims`," but the *return* diverges (`{ access, refresh?,
   expiresIn }` vs `{ identity, access }`), and the refresh grant skips all the
   claims/pkce/hash machinery. it's a **sibling**, not a mirror. naming it as if it mirrors
   may mislead a reader into expecting `identity`.

2. **the error-classification is the real work, and it retro-fits the code grant's gap.**
   the extant exchange throws one opaque `UnexpectedCodePathError` for everything. we are
   asked to build a *finer* taxonomy for the refresh path only. that leaves an asymmetry the
   other direction: the code grant stays coarse while the refresh grant gets rich errors.
   tempting to unify both — but that widens scope beyond the wish. flag, don't fix.

3. **`getTokensFromOidcRefreshClaims` may be *thinner* than its wrapper suggests.** because the
   refresh grant needs no verification/pkce, the "wrapper" over an exchange leg is almost
   pass-through. the wrapper-vs-flat call (Q4) is low-stakes but worth a conscious choice so
   we don't add a layer that earns nothing.

4. **`refresh?` in the wish vs the repo's forbid-`undefined` rule.** the wish writes
   `refresh?` (optional), but the repo forbids `undefined` attributes on internal contracts.
   `refresh: string | null` resolves it — a small but real friction between the wish's
   sketch and the house style.
