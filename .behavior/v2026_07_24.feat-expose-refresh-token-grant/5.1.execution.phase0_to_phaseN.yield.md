## follow-on backlog (out-of-scope for this wish, recorded here for durability)

these items were raised across the peer-review trail and correctly held out of scope per the
blueprint's `[○] retain` / wisher-decision verdicts. recorded here — durable beyond the
`.reviews/peer/*.md` files, which do not survive the merge — so the lessons do not evaporate:

1. **harden the code-grant peer `exchangeOidcResponseCodeForTokens.ts`** — the untouched peer
   leg has three latent gaps this feature deliberately did NOT touch (vision "awkward" note #2,
   "flag, don't fix"): (a) no transport `.catch()`; (b) no null/typeof guard before it
   destructures `response.data` (a malformed 2xx throws a raw `TypeError` rather than a typed
   error); (c) it sets `content-type: application/x-www-form-urlencoded` but passes a plain JS
   object as `data` — axios only form-encodes a `URLSearchParams`/`FormData` and otherwise
   `JSON.stringify`s, so this leg likely sends a json body under a form-urlencoded header (masked
   in prod only by provider leniency; it has no test — the integration test is `it.skip`). the
   refresh leg fixed this exact class via a `URLSearchParams` body. the clean fix, once a 3rd
   caller earns it (rule-of-three), is a shared `postOidcTokenGrant` communicator that both legs
   call. tracked here for a future wish; a github issue is the wisher's to open (this driver lacks
   issue-create permission, and issue-create is an external, visible action i do not take
   autonomously).

2. **brand `provider.tokenEndpoint` as `Rfc6749TokenEndpoint`** — today a bare `string`, so a
   caller can pass facebook's non-conformant endpoint and it compiles, then fails only at runtime
   as a typed `OidcToken*` error. the proportionate guardrail for THIS wish is the JSDoc caveat +
   the registry comment + the typed failure (all present). a branded type that rejects a
   non-rfc-6749 endpoint at compile time is a cleaner guard — a wisher-level decision, deferred.

3. **rename `response/` → `grant/` if a 3rd grant-type orchestrator ever lands** — the new
   orchestrator sits beside its 1:1 peer `getTokensFromOidcResponseClaims.ts` under `response/`.
   defensible by that precedent now; if a 3rd public token orchestrator is ever added, `response/`
   stops to mean "OIDC response" and a rename reads cleaner. no action now — flagged for that
   future trigger.

4. **unify the operator-credentials shape `{ oidcClientId, oidcClientSecret }` across both grant
   legs** — the shape is now spelled independently in 4 sites (2 code-grant, 2 refresh-grant).
   within THIS wish's scope it appears only twice, so wet is correct per rule-of-three; but
   system-wide the bar is crossed. the clean fix is one documented `OidcOperatorCredentials` type
   referenced by all four, landed together with item 1's code-grant work (so the retained peer is
   touched once, intentionally, not as scope creep here).

5. **surface `refresh` on the code-grant leg (offline-access capture)** — `getTokensFromOidc`
   `ResponseClaims` returns `{ identity, access }` and `getOidcAuthenticationRequestUri` never
   sends `access_type=offline` / `prompt=consent`, so this library's code-grant leg does not
   itself capture the initial refresh token that the refresh grant then spends. for the keyrack
   daily-cron usecase the initial token is provisioned out-of-band (offline-access grant), which
   the readme step-6 note now states plainly. a follow-on to add `access_type`/`prompt` support to
   the request leg + a `refresh` field on the code-grant return would let a consumer produce the
   initial token through this library end to end — a wisher-scoped decision, deferred.
